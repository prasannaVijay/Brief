Start here

How does a frozen model tell you today's headlines?

Its weights were baked months ago. It has no network, no memory, no clock. Yet somehow agents pull live data all day.

The answer is the foundation of every connection Brief will ever make.

The reveal

It doesn't fetch anything. It asks you to.

You hand the model a menu of tools it's allowed to call. When it wants data, it doesn't run code — it emits a structured request: "call get_headlines with this url." Your code makes the real API call and hands the result back.

This is "function calling" / "tool use" — the mechanism under every LLM-to-API connection.

The model supplies the intent; your code supplies the reach. It never touches the network itself.

What a tool actually is

A name, a description, and a schema.

That's all the model sees of a tool: what it's called, what it does in plain words, and the shape of its arguments. No implementation — just the contract.

So the description drives the behavior. A vague docstring makes the model call wrong or not at all. This is prompt-writing, not just plumbing — keep it in mind for the build.

The problem

Hand-wired, it explodes.

3 apps × 3 clients = 9 bespoke integrations — and you rebuild them for every new model or framework. That's the M × N trap.

The fix

MCP: build once, plug in anywhere.

3 + 3 = 6, through one standard. Build a server once and any MCP client can use it — no custom glue. The "USB-C for AI."

Why this is a Brief story

Every surface becomes a server. Brief becomes a host.

Google, Slack, your notes, that internal API nobody wants to touch — each is just an MCP server. Brief connects to them as a host and never cares how they're built inside.

Today you build one server with one tool — get_headlines, which also happens to be a real Brief surface.

Hands on

Let's build get_headlines.

One tool that pulls the top items from any RSS feed. We'll run it locally, prove it in the Inspector, then call it live from Claude Desktop.

No agent required yet — a real MCP client drives your server, so you see it work end to end today.

Setup · one time

Two dependencies. That's it.

$ uv add fastmcp feedparser # also handy: Python 3.12, Claude Desktop, and Node (for the Inspector)

FastMCP is the library behind most MCP servers — it turns a plain Python function into a spec-compliant tool. feedparser just reads RSS.

The whole server

This is all of it.

from fastmcp import FastMCP
import feedparser

mcp = FastMCP("brief-tools")

@mcp.tool
def get_headlines(feed_url: str, limit: int = 5) -> str:
    """Get the latest headlines from an RSS feed."""
    feed = feedparser.parse(feed_url)
    items = feed.entries[:limit]
    return "\n".join(f"- {i.title} ({i.link})" for i in items)

if __name__ == "__main__":
    mcp.run()
Reading it

Four lines do the real work.

  • 1FastMCP("brief-tools") — names your server. That's the whole setup.
  • 2@mcp.tool — registers the function as a callable tool. No schema to hand-write.
  • 3The docstring + type hints become the schema the model sees — remember slide 6? This is where the description lives.
  • 4return a string, and mcp.run() starts it over stdio, ready for any client.

Return text, not a raw dict — a dict can look fine in the Inspector but arrive truncated in Claude Desktop.

Prove it · step 1

Validate in the MCP Inspector.

$ fastmcp dev server.py # opens the Inspector in your browser

Pick get_headlines, paste an RSS url, hit Run — and watch the headlines come back. Notice the schema it auto-generated from your function: that's discovery at work.

The Inspector is your debugger before any model is involved. If it works here, the tool is sound.

Prove it · step 2

Now let Claude use it.

$ fastmcp install claude-desktop server.py # registers your server

What it does: writes an entry into Claude Desktop's config file (claude_desktop_config.json, under mcpServers) with the command to launch your server over stdio. On restart, the app spawns server.py as a subprocess and discovers its tools. You could hand-edit that JSON yourself — this just does it for you.

Restart Claude Desktop and ask: "what are today's headlines from <feed>?" — and watch it call your tool and answer from live data.

Two gotchas that eat time: if a tool shells out, capture the subprocess output (stdout collides with the stdio transport otherwise); and Claude Desktop's launcher is picky about the Python path.

Before you go

Start narrow. Stay honest.

A tool the model can call is real power — so begin read-only, scope it tightly, and treat any live text as untrusted (prompt injection is real once data flows in). Promote to HTTP and auth only when a second consumer needs it.

Checkpoint: mcp-server-v1. Next time, Brief becomes the host that consumes servers like yours. Bring a tool idea.
